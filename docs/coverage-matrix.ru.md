# Матрица покрытия

[English](coverage-matrix.md) | Русский

Система под тестом: Vikunja v2.6.0, поднимается локально из `docker/docker-compose.yml`.

Этот документ говорит, что проверяется, на каком уровне и зачем. Каждый тест набора объявляет проверки, которые он даёт, отчёт ссылается на строки ниже, а проверка без тестов видна в сводке прогона. Документ и набор не могут молча разойтись: `tests/unit/test_documentation.py` роняет сборку, если это случилось.

---

## 1. Принцип, из которого всё следует

Если умножить 170 операций на 12 актёров и на 16 видов проверки, получатся десятки тысяч сочетаний, половина из которых не проверяет ничего. Вместо этого покрытие разделено на два слоя разной природы.

**Широкий неглубокий слой, генерируемый из описаний самого продукта.** Проверка контракта, требование учётных данных на каждой операции и матрица scope'ов API-токенов применяются ко всем операциям автоматически. Руками там не написано ничего, и новый эндпоинт продукта покрыт в день своего появления.

**Узкий глубокий слой, написанный руками вдоль хребта.** Хребет — это набор ресурсов, где живёт логика прав и куда приходились опубликованные уязвимости. Только для них есть полная матрица доступа, проверка через базу и контроль побочных эффектов.

Это разделение — главное решение документа. Из-за него же набор примерно из тысячи проверок покрывает продукт лучше, чем покрыл бы набор из трёх тысяч.

## 2. Хребет

| Ресурс | Почему он на хребте |
|---|---|
| project | корень модели прав; всё остальное наследует от него |
| task | основная сущность, доступ к ней вычисляется через проект |
| attachment | сюда пришлась CVE-2026-33678: чтение по одному идентификатору |
| comment | вложенный ресурс со своей проверкой прав |
| bucket и view | сюда пришлась CVE-2026-55065: разрушение чужой доски |
| link share | звено в цепочке GHSA-2pv8-4c52-mf8j |
| api token | сюда пришлась CVE-2026-68581: захват чужих токенов |
| team | второй путь к доступу, помимо прямой выдачи |
| relation | связывает задачи между проектами, классическая утечка |
| reaction | полиморфный эндпоинт с типом сущности в пути |

Вне хребта: миграции, администрирование инстанса, фоновые изображения из фотостока, аватары. Им достаётся только smoke-покрытие.

## 3. Актёры

| Код | Кто | Как получается |
|---|---|---|
| `owner` | создал проект | регистрация, затем создание |
| `admin_member` | выдан Admin | прямая выдача пользователю |
| `write_member` | выдан Write | прямая выдача пользователю |
| `read_member` | выдан Read | прямая выдача пользователю |
| `team_write` | доступ через команду | членство в команде с Write |
| `outsider` | вошёл в систему, к проекту отношения не имеет | отдельная регистрация |
| `anon` | без учётных данных | запрос без заголовка |
| `share_read` | публичная ссылка, чтение | хеш, обменянный на токен |
| `share_write` | публичная ссылка, запись | хеш, обменянный на токен |
| `share_pwd` | ссылка под паролем | хеш и пароль, обменянные на токен |
| `token_narrow` | API-токен с одним узким правом | токен, выпущенный на одну область |
| `instance_admin` | администратор инстанса | не перебирается: см. ниже |

Уровни прав в продукте: чтение — ноль, запись — один, админ — два, и есть четвёртое состояние, «не определено», это минус один. Модель защищает от того, чтобы пустое значение в JSON молча превратилось в доступ на чтение. Граница разбора этого поля проверяется отдельно.

У публичных ссылок две независимые оси: уровень прав и наличие пароля. Перебираются обе.

`instance_admin` — единственный актёр, которого матрица не перебирает, и причину стоит назвать, а не прятать. Единственный путь к этому флагу снаружи базы — тестовый эндпоинт продукта, заполняющий таблицы: он заменяет содержимое таблицы целиком. Применённый к таблице пользователей, он уничтожил бы учётные записи, под которыми идут все остальные тесты, поэтому набор к нему не тянется. Маршруты, доступные только администратору, всё равно покрыты генерируемыми семействами, которые требуют учётных данных от каждой операции.

## 4. Проверки <a id="checks"></a>

Каждая строка — вид проверки. Тест объявляет те, что он даёт, через `@pytest.mark.covers("ACL")`, и получает соответствующий маркер отбора (`pytest -m acl`), серьёзность из приоритета ниже и ссылку из отчёта на эту строку. «Тесты» — это то, что набор прогоняет сегодня, посчитанное по полному прогону.

| Код | Проверка | Как | Приоритет | Тесты |
|---|---|---|---|---|
| <a id="con"></a>`CON` | Ответы соответствуют своему контракту | генерируется | P0 | 362 |
| <a id="aut"></a>`AUT` | Каждая операция требует учётных данных | генерируется | P0 | 349 |
| <a id="err"></a>`ERR` | Доменные коды ошибок сохраняются | генерируется | P0 | 49 |
| <a id="scp"></a>`SCP` | Scope'ы API-токенов соблюдаются | генерируется | P0 | 37 |
| <a id="acl"></a>`ACL` | Матрица доступа | таблицей | P0 | 49 |
| <a id="int"></a>`INT` | Целостность данных, проверяется в базе | руками | P0 | 6 |
| <a id="cve"></a>`CVE` | Регрессии на опубликованные уязвимости | руками | P0 | 5 |
| <a id="fun"></a>`FUN` | Бизнес-правила | руками | P1 | 8 |

| <a id="asy"></a>`ASY` | Асинхронные побочные эффекты | руками | P1 | 6 |
| <a id="xvr"></a>`XVR` | Согласованность версий API | руками | P1 | 9 |
| <a id="ui"></a>`UI` | Поведение, которое проверяется только браузером | Playwright | P1 | 4 |
| <a id="cnc"></a>`CNC` | Конкурентность и идемпотентность | руками | P2 | 5 |
| <a id="i18"></a>`I18` | Языки, часовые пояса и форматы | Playwright | P2 | 4 |
| <a id="dav"></a>`DAV` | Календарный протокол, тонкий срез | руками | P2 | 16 |

Приоритет читается в отчёте как серьёзность: P0 — критическая, P1 — обычная, P2 — незначительная.

**Где набор находится сейчас.** За каждой строкой стоят тесты, и ни одна из них не стоит там для галочки. Основной счёт держат генерируемые семейства, и это работающий замысел, а не перекос: они покрывают все операции, которые публикует продукт, и ничего не стоят в поддержке.

CI-джоб api запускается с `--fail-uncovered P0`, поэтому строка P0, упавшая до нуля, красит сборку в красный. Это не гипотеза. `SCP` неделями стоял на нуле, и никто этого не замечал, потому что семейство отваливалось на сборе тестов из-за `KeyError` длиной в одну строку.

## 6. Матрица доступа

Строится один раз как таблица данных и исполняется параметрами. Строка — это ресурс, операция, актёр и ожидаемый статус.

Один проект создаётся один раз на модуль, и до него добираются всеми путями, которые предлагает продукт: прямая выдача каждого уровня, команда, публичная ссылка на чтение, посторонний и анонимный вызов. Строки в том виде, в каком набор прогоняет их сегодня:

| Операция | owner | admin | writer | reader | teammate | share_read | share_write | share_pwd | token_narrow | outsider | anon |
|---|---|---|---|---|---|---|---|---|---|---|---|
| прочитать задачу | 200 | 200 | 200 | 200 | 200 | 200 | 200 | 200 | 200 | 403 | 401 |
| обновить задачу | 200 | 200 | 200 | 403 | 200 | 403 | 200 | 403 | 401 | 403 | 401 |
| удалить задачу | 200 | 200 | 200 | 403 | 200 | 403 | 200 | 403 | 401 | 403 | 401 |
| удалить проект | 200 | 200 | 403 | 403 | 403 | 403 | 403 | 403 | 401 | 403 | 401 |

`token_narrow` — строка, которую стоит прочитать дважды. Токен, несущий одно действие на одной области, получает за её пределами **401**, а не 403: продукт вовсе отказывается принимать эти учётные данные для такого маршрута, вместо того чтобы принять их и затем взвешивать права.

Удаление проекта разделено надвое. Отказы проигрываются на общем проекте, потому что отклонённый вызов ничего не меняет; двум строкам, которые проходят, достаётся свой отдельный мир, так как проект, созданный ради одной строки, не нёс бы ни одной из общих выдач. Строке, которая меняет данные, достаётся запасная задача, по той же причине.

Здесь перебираются все актёры из раздела 3, кроме администратора инстанса, по названной там причине.

**Разница между 403 и 404 считается отдельным классом дефекта.** Посторонний, который получает «запрещено» вместо «не найдено», узнал, что чужой объект существует. Продукт отвечает 403, и набор фиксирует позицию как ожидаемое падение, а не утверждает её: см. заметку о придержанной находке в [docs/findings](findings/README.md).

## 7. Генерируемые семейства

Четыре семейства, которых никто не пишет руками.

**CON, соответствие контракту.** Описания забираются с работающего инстанса: v1 отдаёт Swagger 2.0, v2 отдаёт OpenAPI 3.1, который Huma генерирует на лету. Каждый ответ на каждый вызов, сделанный любым тестом, валидируется по схеме своей операции — на транспортном уровне, а не в отдельном тесте. Сверх того один проход обходит все операции чтения.

**AUT, нужны учётные данные.** Каждая операция, вызванная без заголовка авторизации. Ожидание — 401 и ничего утёкшего в теле. Список намеренных исключений задан явно и сам проверяется на устаревание, поэтому эндпоинт, который молча стал публичным, не проскочит.

**SCP, матрица scope'ов токена.** API-токен несёт права как отображение области в действия, и продукт публикует полный набор допустимых ключей на отдельном эндпоинте. Поэтому матрица строится из ответа самого продукта: на каждую область выпускается токен ровно с одним действием, и то, что это действие разрешает, должно пройти, а всё соседнее — получить отказ.

**ERR, инвариант доменного кода ошибки.** Продукт несёт числовой доменный код, по которому клиенты переводят сообщения. v1 возвращает его полем `code`. v2 отдаёт ошибки в формате RFC 9457 и переносит тот же код, иначе клиенты v2 читают ноль. Инвариант: там, где v1 называет отказ доменным кодом, v2 обязана назвать его тем же самым, а любой путь ошибки, обходящий перевод, всплывает отсутствующим или другим кодом.

Пары вычисляются, а не перечисляются. Две версии описывают одну и ту же операцию под разными именами параметров, `/projects/{projectID}/users/{userID}` против `/projects/{project}/users/{user}`, поэтому сопоставление по буквальному шаблону находит едва половину общего, а сопоставление по форме пути находит остальное. Каждая пара, у которой можно спросить об идентификаторе, который не может существовать, спрашивается на обеих версиях и держится одного и того же ответа. Остальное формулируют две проверки рядом с обходом: что отсутствующий объект код несёт, а отказ — нет ([VKJ-005](findings/VKJ-005-permission-errors-carry-no-code/)).

Обход нашёл [VKJ-016](findings/VKJ-016-caldav-token-revocation-false-success/) на первом же прогоне, и это довод за то, чтобы такое порождать, а не писать.

## 8. Прицельные места

**Массовые операции.** Три эндпоинта принимают список: массовое обновление задач, массовая простановка меток, массовое назначение исполнителей. Классический дефект этого класса — проверка прав только на первом элементе. Сценарий: два объекта, права есть на один и нет на второй. Ожидание — отказ всему вызову, ничего не применено частично, и это подтверждается по базе.

**Полиморфный эндпоинт реакций.** Тип сущности приходит в пути. Проверяется с другим типом, с несуществующим типом и с типом, к которому у актёра нет доступа.

**Связи между задачами.** Связь создаётся между задачами в разных проектах. Проверяется: привязка своей задачи к чужой и утечка содержимого чужой задачи через список связей.

**Публичные ссылки.** Хеш из сорока символов, который генерирует сервер. Цепочка «раскрыть хеш, а затем дотянуться до вложений другого проекта» была настоящей уязвимостью. Проверяется: область действия токена ссылки и поведение ссылки под паролем.

**Разбор уровня прав.** Null, пустая строка, число строкой, сторожевое значение «не определено», значение вне диапазона, дробное, булево, список и объект. Ничто из этого не должно стать выданным правом, а отказ обязан оставить уже выданное нетронутым. Если уровень не назван вовсе, право ложится на чтение, и это безопасное направление для значения по умолчанию.

**Формат API-токена.** Токен — это префикс `tk_` и сорок шестнадцатеричных символов; поиск идёт по последним восьми, а дальше сравнение хешей. Код защищён от значения, которое слишком короткое, чтобы его нарезать. Проверяется: пустой, только префикс, слишком короткий для нарезки, верной формы с неверным значением, верной формы, но не шестнадцатеричный, с неверным префиксом, без префикса, из четырёх тысяч символов и со знаками препинания. Каждый получает отказ одинаково, с тем же статусом и тем же доменным кодом, потому что отказ, который меняется от формы значения, сообщает угадывающему, какая половина догадки была верной.

**Генерируемые эндпоинты частичного обновления.** v2 выводит их автоматически из пар чтения и записи. Вдоль хребта частичное обновление сравнивается с полным.

**Что обещает задача.** Правила, которые пользователь описал бы, не упоминая HTTP, и которые не проверяет ни один код статуса: завершение задачи записывает, когда это случилось, а повторное открытие это забывает; повторяющаяся задача сдвигает свой срок вместо того, чтобы закрыться; задача несёт собственный номер, который растёт внутри своего проекта и начинается заново в следующем; перенос карточки в колонку Done — то же самое действие, что и галочка; архивный проект отказывает записи и остаётся читаемым; исполнителем может быть только тот, кто может открыть задачу; связь видна с обоих своих концов; одна метка ложится на одну задачу один раз.

**Два вызывающих в один и тот же момент.** Обычный случай для продукта, которым пользуются сообща, и тот, до которого последовательный набор не добирается никогда. Вызывающие отпускаются вместе барьером, потому что работа, отданная пулу потоков, расползается по времени, а разнесённые вызовы не сталкиваются. Что обязано выполняться, кто бы ни выиграл: принятые задачи сохраняют разные номера, одновременные обновления оставляют одну из записей целой, а ни двойное удаление, ни двойная простановка метки не отвечают ошибкой сервера. Не выполняется [VKJ-015](findings/VKJ-015-simultaneous-task-creation-500/): две задачи, созданные в одном проекте в один и тот же момент, сталкиваются на этом номере, и все вызывающие, кроме одного, получают 500.

## 9. Согласованность версий API

Срез, уникальный для этой системы под тестом, где два API описывают один и тот же продукт.

Различия, которые сделаны намеренно и подтверждены по исходникам продукта:

1. v1 использует нестандартные глаголы: обновление — POST, создание — PUT. v2 — обычный REST.
2. Форма ошибки разная: v1 возвращает плоский объект с кодом и сообщением, v2 возвращает документ RFC 9457.
3. **Ошибки валидации несут разные статусы: v1 отвечает 412, v2 отвечает 422.** Это решение авторов, а не дефект, и оно зафиксировано как ожидание.

Что проверяется:

1. Создать через v1, прочитать через v2, сравнить все поля.
2. То же в обратную сторону.
3. Один актёр получает одинаковое решение о доступе от обеих версий.
4. Доменный код ошибки совпадает при разных статусах и разной форме тела.
5. Пагинация ведёт себя одинаково на границах; размер страницы по умолчанию — пятьдесят.
6. Поля с датами приходят в одном формате и в одной зоне.

---

## 10. Проверки через базу данных

| Что | Как |
|---|---|
| удаление проекта не оставляет осиротевших задач | подсчёт строк по внешнему ключу |
| отклонённое массовое обновление не применило ничего, даже частично | сравнение всех строк до и после |
| выданное право записано строкой | выборка из таблицы прав |
| вложение записано за своей задачей | join таблиц вложений и файлов |
| токен нигде не хранится в открытом виде | выборка колонок таблицы токенов |
| обратное чтение токена никогда не возвращает секрет | ответ API рядом с сохранённой строкой |

Только чтение, всегда. Набор никогда не пишет по этому пути: готовить состояние не через собственное API продукта значило бы тестировать схему, а не продукт, и это рассыпалось бы на первой же миграции.

## 11. Асинхронные эффекты

Каждая проверка ждёт результата с дедлайном. Фиксированных пауз в наборе нет ни одной.

| Эффект | Где подтверждается |
|---|---|
| письмо о регистрации | API почтовой ловушки, и токен из письма гасится |
| письмо о сбросе пароля | API почтовой ловушки |
| исходящий вебхук на событие задачи | свой приёмник, отдельный на тест, тело сравнивается |
| вебхук игнорирует событие, на которое не подписан | тот же приёмник, он должен остаться пустым |
| вложение доезжает до объектного хранилища | забирается обратно и сравнивается побайтово |
| счётчик метрики сдвинулся | запрос в Prometheus |

Внутренняя шина событий продукта работает в процессе, поэтому событие и его обработчик живут в одном контейнере. Это сокращает ожидание, но не отменяет его: обработчики асинхронные, и тестовое API самого продукта намеренно дожидается их перед тем, как менять данные.

## 12. Регрессии на опубликованные уязвимости

Каждый тест называет свой advisory, поэтому падение здесь — не загадка. Оно говорит, какая опубликованная слабость вернулась.

| Идентификатор | Что это было | Проверка |
|---|---|---|
| CVE-2026-33678 | чтение вложения по одному идентификатору | до чужого вложения не дотянуться |
| GHSA-2pv8-4c52-mf8j | раскрытие хеша плюс доступ к чужим вложениям | токен ссылки заперт в своём проекте |
| CVE-2026-68581 | захват API-токенов других пользователей | чужой токен нельзя ни прочитать, ни отозвать |
| CVE-2026-55065 | разрушение чужих kanban-бакетов | операции над бакетами требуют прав на проект |
| CVE-2026-35601 | перевод строки ломает генерацию календаря | заголовок с управляющими символами экранируется |
| CVE-2026-27819 | распаковка архива за пределы своей директории | вне области, только отмечено |

## 13. Календарный протокол, тонкий срез

Шестнадцать проверок. Смысл среза одной фразой: **у одних и тех же данных две двери, и они обязаны сходиться.**

1. Задача, созданная через API, видна через CalDAV, и наоборот.
2. Срок, выставленный в одной двери, доезжает до другой, в обе стороны.
3. Удаление в одной двери — это удаление в другой, в обе стороны.
4. Заголовок вне латиницы переживает обе стороны без изменений.
5. Заголовок с переводом строки не может подделать свойства календаря: регрессия на CVE-2026-35601.
6. Календарь отказывает вызову без учётных данных и запрашивает Basic.
7. Чужой календарь не читается ни через GET, ни через PROPFIND.
8. Отозванный CalDAV-токен перестаёт работать.
9. API-токен открывает календарь, только когда несёт право `caldav`, и только под именем своего владельца.

Ответы читаются по правилам RFC 5545, а не поиском по тексту: правильно экранированный заголовок всё равно содержит символы того свойства, которое он пытался подделать, и отличить настоящее свойство от текста, который на него похож, можно только разбором.

## 14. Локализация и время

| Что | Проверка |
|---|---|
| интерфейс следует языку браузера | placeholder меняется с английского для de-DE и ru-RU |
| локаль самого набора закреплена | контекст по умолчанию отрисовывает английские формулировки |
| длинные слова не ломают вёрстку | измеряется, а не осматривается на глаз: элемент либо помещается, либо обрезается |

Закреплены только английские формулировки. Для остальных языков проверка в том, что формулировка вообще изменилась, потому что утверждать конкретный перевод значило бы тестировать переводчиков, а не продукт.

## 15. Поведение при отказе зависимости

**Отдельный слой со своим прогоном.** Он никогда не присоединяется к основному, потому что выбивает инфраструктуру из-под себя: такие проверки медленные и нестабильные по природе. Он идёт отдельным CI-джобом, по расписанию и по требованию, и всегда в один процесс, потому что отказ невозможно удержать внутри того теста, который его вызвал.

| Отказ | Ожидание | Что происходит на самом деле |
|---|---|---|
| база данных пропала | health-check перестаёт заявлять, что всё здорово, и наружу не вылезает stack trace | как ожидается |
| Redis пропал | продукт деградирует, но продолжает отвечать | вместо этого он виснет: [VKJ-011](findings/VKJ-011-redis-outage-hangs-every-request/) |
| объектное хранилище пропало | загрузка падает с внятной ошибкой | он отвечает 200, спрятав отказ в теле: [VKJ-010](findings/VKJ-010-failed-upload-returns-200/) |
| почтовый сервер пропал | запрос не падает, письмо ждёт | запрос держится, но почта встаёт до паузы в трафике: [VKJ-013](findings/VKJ-013-mail-daemon-stale-connection/) |

Три ожидания из четырёх не выполняются, и это неплохая отдача от шести тестов.

## 16. Интерфейс

Только то, что нельзя проверить через API. Данные готовятся вызовами API, а session storage браузера заполняется заранее, поэтому страница открывается уже под учётной записью и сразу на том, что рассматривается.

1. Быстрое добавление вытаскивает метку и приоритет из обычной фразы и убирает маркеры из заголовка.
2. Задача появляется больше чем в одном представлении своего проекта.
3. Проект, отданный по ссылке только на чтение, не предлагает элемента управления для добавления задачи.
4. Язык и вёрстка, как в разделе 14.

Большой браузерный набор, дублирующий покрытие API, был бы медленнее, хрупче и стоил бы меньше. Этот намеренно маленький.

## 17. Как оформляются находки

Находки лежат в `docs/findings`, по папке на каждую, на английском и с русской версией рядом.

Требование к каждому отчёту: **воспроизводится за две минуты и без доверия к автору.** Читатель запускает скрипт и видит результат.

```
docs/findings/
  README.md                    индекс
  VKJ-007-label-update-verb/
    README.md                  отчёт
    README.ru.md               то же самое по-русски
    reproduce.py               самостоятельное воспроизведение, только стандартная библиотека
```

Поля отчёта: суть, серьёзность, затронутая версия, окружение, шаги, ожидаемый результат, фактический результат, влияние на пользователя и тест, который это фиксирует.

**Исключение для уязвимостей.** Если находка выглядит эксплуатируемой, то есть даёт доступ к чужим данным или обходит проверку прав, она сначала уходит сопровождающим продукта по их опубликованной процедуре и попадает в эту папку только после исправления. Публиковать рабочую дыру в живом продукте нельзя.

## 18. Что намеренно не покрывается

- Импорт из внешних систем: для него нужны учётные данные этих систем.
- Фоновые изображения из внешнего фотосервиса, по той же причине.
- Плагины на встроенном интерпретаторе: большая отдельная тема.
- Нагрузка и характеристики производительности: другой инструмент и другая работа.
- Собственные юнит-тесты продукта: их написали его авторы.
- Полное соответствие CalDAV: намеренно ограничено срезом из раздела 13.
