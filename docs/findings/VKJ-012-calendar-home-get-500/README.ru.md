# VKJ-012. GET на корень календарей CalDAV отвечает 500

[English](README.md) | Русский

**Серьёзность:** низкая
**Версия:** Vikunja v2.6.0
**Компонент:** CalDAV, корневая коллекция календарей `/dav/projects/`
**Окружение:** официальный образ `vikunja/vikunja:2.6.0`, CalDAV включён (по умолчанию), стенд из `docker/docker-compose.yml`

## Суть

Авторизованный `GET` или `HEAD` на корень календарей, `/dav/projects/` со слешем на конце и без, отвечает **500 Internal Server Error** с пустым телом. `PROPFIND` на ту же коллекцию с теми же учётными данными отвечает 207 и перечисляет проекты.

```
PROPFIND /dav/projects/   207   286 байт
GET      /dav/projects/   500     0 байт
HEAD     /dav/projects/   500     0 байт
GET      /dav/projects    500     0 байт
```

Продукт пишет эти запросы в журнал на уровне INFO без текста ошибки, так что в логах отказ тоже не виден.

## Влияние

Календарные клиенты находят коллекции через `PROPFIND`, поэтому обычная синхронизация по этому пути не ходит. Отсюда низкая серьёзность.

Всё остальное, что обращается к адресу, на ошибку попадает. Человек, открывший адрес CalDAV со страницы настроек в браузере, обычный WebDAV-клиент, проба мониторинга или проверка здоровья на обратном прокси получают серверную ошибку. Администратор при этом не находит в логах ничего, что её объясняет, а любые оповещения по кодам ответа считают пятисотку отказом сервера.

## Шаги воспроизведения

1. Поднять стенд.
2. Зарегистрировать и подтвердить учётную запись.
3. Отправить `GET /dav/projects/` с учётными данными этой записи через HTTP Basic.
4. Для сравнения отправить `PROPFIND /dav/projects/` с заголовком `Depth: 1` и теми же данными.

`reproduce.py` в этой папке делает всё это на одной стандартной библиотеке:

```bash
py docs/findings/VKJ-012-calendar-home-get-500/reproduce.py
```

## Ожидаемый результат

`GET` на коллекцию отвечает содержимым либо кодом 404 или 405, если сервер содержимого не отдаёт. Кодом 500 он не отвечает.

## Фактический результат

500 с пустым телом, для `GET` и `HEAD`, со слешем на конце и без.

## Причина по исходному коду

`ProjectHandler` обслуживает и `/dav/projects`, и `/dav/projects/:project`. Если проекта в пути нет, `getProjectFromParam` возвращает пустой проект с идентификатором 0. На `GET` метод `GetResource` запускает для него проверку чтения коллекции, `CanRead` ищет проект, и `requireProjectsByIDs` падает с `ErrProjectDoesNotExist{ID: 0}`. Это не та ошибка «не найдено», которую понимает caldav-go, а любую другую ошибку хранилища caldav-go превращает в 500. Об этом прямо сказано в комментарии в коде хранилища.

`PROPFIND` до этой проверки не доходит: у `GetResources` есть отдельная ветка для корневой коллекции.

## Что чинить

Обрабатывать корневую коллекцию на `GET` и `HEAD` явно, как это уже сделано для `PROPFIND`: отвечать 405 или пустым календарём. Отдельно стоит писать в журнал исходную ошибку, когда caldav-go отдаёт 500: тогда администратор увидел бы проблему сам.

## Связанный тест

`tests/api/calendar/test_calendar_access.py::test_the_calendar_home_answers_a_plain_get_without_a_server_error`, помечен как ожидаемо падающий. Позиция зафиксирована, сборку не ломает, и тест превратится в неожиданный успех, как только корень перестанет отвечать 500.
