# VKJ-017. Обновление одного проекта переписывает все проекты инстанса

[English](README.md) | Русский

**Серьёзность:** высокая
**Версия:** Vikunja v2.6.0
**Компонент:** проекты, путь обновления
**Окружение:** официальный образ `vikunja/vikunja:2.6.0`, стенд из `docker/docker-compose.yml`

## Суть

Переименование проекта — да и любое обновление одного поля — заставляет продукт переписать колонки `position` и `updated` у **каждой строки таблицы проектов**, включая проекты аккаунтов, не имеющих к происходящему никакого отношения.

Измерено на стенде с 12 848 проектами, принадлежащими 9 449 аккаунтам. Одно переименование:

| | |
|---|---|
| строк, у которых изменился `updated` | **12 847** из 12 848 |
| различных владельцев, чьи проекты переписаны | **9 449** |
| сам переименованный проект среди них | нет |
| сколько заняло запрос | **4,94 с** |

База показывает форму прямо. Выборка из `pg_stat_activity` во время запроса находит один оператор, выполняемый снова и снова:

```sql
UPDATE "public"."projects" SET "position" = $1, "updated" = $2 WHERE (id = $3)
```

По оператору на проект, а не один на тот проект, который меняют.

Стоимость линейна по числу проектов инстанса и не зависит ни от редактируемого проекта, ни от того, кто им владеет:

| проектов на инстансе | одно переименование | переписано строк |
|---|---|---|
| 10 | 0,017 с | 8 |
| 100 | 0,056 с | 100 |
| 500 | 0,194 с | 496 |
| 1 500 | 0,587 с | 1 500 |
| 12 848 | 4,940 с | 12 847 |

Около 0,4 мс каждого переименования приходится на каждый уже существующий проект. Создание проекта стоит 57 мс, чтение — 7 мс, при любом размере: дело только в пути обновления.

## Влияние

Три следствия, по возрастанию тяжести.

**Замедление без предела.** На десяти тысячах проектов переименование занимает пять секунд. Размера, на котором оно перестанет расти, нет: работа пропорциональна таблице.

**Запись в чужие строки.** `updated` — поле, которое API отдаёт и которое читают клиенты. Пользователь, не трогавший свой проект год, видит его изменённым, потому что посторонний аккаунт в посторонней организации что-то переименовал. Любой клиент, синхронизирующийся по времени изменения — включая собственную дверь CalDAV этого же продукта, — получает сигнал, что изменилось всё. `position`, определяющий порядок показа проектов, переписывается всем одновременно.

**Конкуренция на записи.** Тысячи обновлений строк в одном запросе означают, что блокировки одного переименования накрывают всю таблицу. Параллельные писатели выстраиваются в очередь, а на нагруженном инстансе переименование может вовсе выйти за таймаут клиента. Так это и нашлось: тест, архивирующий проект, начал изредка падать на восьми параллельных исполнителях, когда на стенде накопилось достаточно проектов.

## Воспроизведение

```bash
py docs/findings/VKJ-017-project-update-rewrites-every-project/reproduce.py
```

Скрипту не нужен доступ к базе, он занимает около тридцати секунд. Регистрирует два аккаунта, первым переименовывает его собственный проект, а затем читает через API проект второго аккаунта и показывает, что `updated` и `position` изменились. Потом создаёт ещё пятьсот проектов и повторяет то же самое переименование, показывая, что тот же вызов стал измеримо медленнее.

## Что чинить

Переименование должно обновлять одну строку. Если позицию нужно назначить — назначить её изменяемому проекту; у остальных строк позиции уже есть, и новых они не просили.

Общее решение для такой формы обычное: дать `position` разреженный порядок, чтобы один элемент можно было поставить между соседями, не перенумеровывая остальных, и пересчитывать весь набор, только когда зазоры действительно кончились. Какой бы ни была схема, пересчёт должен ограничиваться проектами, которые видит вызывающий. Выход за пределы своего аккаунта неверен сам по себе, безотносительно скорости.

## Границы находки

Только обновление проектов. Создание так не делает, чтение тоже, обновление задачи тоже. Остальные пути записи набора измерены при том же размере инстанса и остались в десятках миллисекунд.

## Связанный тест

`tests/api/integrity/test_data_integrity.py::test_a_write_by_one_account_leaves_another_accounts_projects_alone`, помечен как ожидаемо падающий. Он формулирует свойство, которое у продукта должно быть — запись одного аккаунта не меняет строки другого, — поэтому в день исправления тест станет неожиданным успехом и скажет об этом.
