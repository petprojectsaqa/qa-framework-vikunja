# VKJ-004. Операции отвечают статусами, которых нет в их описании

[English](README.md) | Русский

**Серьёзность:** низкая
**Версия:** Vikunja v2.6.0
**Компонент:** описание API
**Окружение:** официальный образ `vikunja/vikunja:2.6.0`, стенд из `docker/docker-compose.yml`

## Суть

Часть операций возвращает коды ответа, не перечисленные в их описании. Измерено по всем операциям обоих описаний, после того как порождаемые семейства обошли их целиком: **191 пара «операция и статус»**, на 190 операциях v1 и одной v2.

| Описание | Статус | Операций | Что это |
|---|---|---|---|
| v1 | 401 | 142 | обычный ответ на отсутствующий или протухший токен, по всему защищённому контуру |
| v1 | 404 | 33 | идентификатор, который ни во что не разрешается, на операциях с объявленными только 200, 403 и 500 |
| v1 | 403 | 5 | зеркало строки выше: здесь объявлен 404, а отвечает 403 |
| v1 | 412 | 4 | поле не прошло валидацию (доменный код 2002) и запись в архивный проект (3008) |
| v1 | 400 | 3 | некорректный аргумент, в том числе вид реакции, которого продукт не знает |
| v1 | 405 | 2 | глагол, который описание объявляет, а маршрутизатор не обслуживает |
| v1 | 201 | 1 | `PUT /user/settings/token/caldav` отвечает 201, объявляя 200 |
| v2 | 401 | 1 | `POST /user/export/download` — единственная операция v2 без ответа `default` |

Заметны две вещи. Строка с 401 — основная масса: 401 объявлен всего у двух операций v1, так что читатель описания нигде не узнает, что протухшая сессия вообще документированный исход. А строки 404 и 403 вместе означают, что на тридцати восьми операциях описание перепутало «не найдено» и «не разрешено» местами.

Вторая версия здесь почти чиста, и по структурной причине: 195 из 196 её операций получают общий ответ `default` со своей моделью ошибки, который покрывает любой статус, не названный отдельно.

## Влияние

Потребитель описания не знает, какие ошибки ему обрабатывать. Сгенерированный клиент попадает в ветку «неожиданный ответ» на самом обычном сценарии протухшей сессии. Документация API вводит в заблуждение в той части, которая нужнее всего при интеграции.

## Воспроизведение

```bash
python reproduce.py
```

## Что чинить

Добавить 401 во все защищённые операции описания и 412 туда, где предусловие проверяется. Поскольку 401 применим ко всему защищённому контуру, разумнее описать его один раз общим ответом, а не перечислять в каждой операции.

## Связанный тест

Ловится контрактной проверкой в транспортном слое, вид нарушения «undeclared status». В базовой линии записано как `VKJ-004`.

Раньше эта запись была единственным исключением в базовой линии: она называла вид нарушения и больше ничего, а значит принимала любой недекларированный статус, в любом описании, на любой операции. Это не запись базовой линии, а выключенная проверка: неожиданный 500 на операции, которая его не объявляет, записывался как уже известный.

Теперь это восемь записей, по одной на класс статуса, с числами из таблицы выше. Две самые узкие привязаны к единственной операции, которую описывают, а 405 на `PUT /labels/{id}` переехал в [VKJ-007](../VKJ-007-label-update-verb/), где ему и место. Класс статуса, которого в этом списке нет — 409, 429, неожиданный 500 — это новое отклонение, и прогон становится красным. Написать снова столь же широкую запись не даёт `tests/unit/test_contracts.py::TestBaseline::test_no_entry_switches_a_whole_check_off`.

## Чему это научило сам набор

Сужение вскрыло две наши собственные ошибки, обе прятались за этим шаблоном:

- Читатель описаний оставлял статус только если находил для него JSON-схему, поэтому статус, объявленный без тела — 204 No Content и любая бинарная выгрузка — выглядел недекларированным. Только в v2 таких ответов тридцать семь, и все они попали бы в эту находку.
- А поскольку такие статусы отбрасывались, 204 или выгрузка файла в v2 проваливались к ответу `default` операции, то есть к модели ошибки. До того, чтобы сообщить об успешной выгрузке как о непохожей на ошибку, оставался один шаг.
