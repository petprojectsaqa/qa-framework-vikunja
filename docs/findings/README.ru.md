## Как прогнать воспроизведение

Стенд должен быть поднят:

```bash
docker compose -f docker/docker-compose.yml up -d --quiet-pull
```

Дальше одна команда на всё:

```bash
py scripts/verify_findings.py
```

Или одна находка:

```bash
py scripts/verify_findings.py VKJ-007
```

Запускатель находит скрипты относительно себя, поэтому работает из любой папки, сам проверяет, отвечает ли стенд, и печатает по строке на находку. Если не нашёл ни одного скрипта или стенд молчит, он скажет об этом вслух. Цикл в командной строке по шаблону так не умеет: несовпавший шаблон даёт пустой вывод, неотличимый от полного успеха.

Каждый скрипт запускается и сам по себе, зависимостей у него нет и из фреймворка он ничего не импортирует:

```bash
py docs/findings/VKJ-007-label-update-verb/reproduce.py
```

Он печатает рядом то, что обещает описание продукта, и то, что продукт делает. Код возврата ноль означает, что находка по-прежнему воспроизводится.

Три из них управляют контейнерами стенда через `docker compose`, потому что находка именно об этом: VKJ-010, VKJ-011 и VKJ-013. Контейнер они возвращают на место в блоке `finally`. Остальным не нужно ничего, кроме стенда.

**Про имя интерпретатора.** В PowerShell на Windows команда `python` ведёт на заглушку из Microsoft Store и не запускается, настоящий интерпретатор зовётся `py`. В Git Bash и на Linux работает `python`.

## Проверка на дубликаты

Перед тем как о чём-то сообщать, трекер продукта просмотрен на совпадения. Результат:

- **VKJ-001 частично пересекается с [issue #3316](https://github.com/go-vikunja/vikunja/issues/3316)**, закрытой 29 июля 2026 года. Там та же причина была устранена во второй версии API. Описание первой версии осталось как было, поэтому находка остаётся в силе, но сообщать о ней нужно как о продолжении закрытой issue, а не как о новом дефекте.
- **VKJ-013 соседствует с [issue #48](https://github.com/go-vikunja/vikunja/issues/48)**, закрытой, где сообщалось о той же строке в журнале, `not connected to SMTP server`, с пути закрытия соединения, пока почта ещё доставлялась. Потери сообщений после перезапуска в том сообщении нет.
- У остальных совпадений в трекере нет. Поиск охватывал описание API, формат ошибок, статусы 401, 403, 404 и 405, нуллевость полей, сбои разбора у сгенерированных клиентов, CalDAV, доставку почты после отказа и уникальное ограничение, стоящее за VKJ-015.
- Версия 2.6.0 на момент проверки была последним выпуском, то есть всё найденное относится к актуальному.

## Статус: в трекер не отправлено

Находки сознательно не заведены как issue. Причина в требованиях проекта к вкладу, описанных ниже: они разумны, но соблюсти их для четырнадцати сообщений стоит больше времени, чем это оправдано прямо сейчас. Короткие черновики написаны и лежат в бэклоге.

На ценность самих находок это не влияет. Каждая подтверждается запуском одной команды на чистом стенде, поэтому читателю не нужно ничьё одобрение, чтобы в неё поверить.

## Правила проекта по вкладу

У Vikunja в `CONTRIBUTING.md` есть отдельный раздел про участие ИИ, и он задаёт рамку для любого сообщения, сделанного с его помощью:

- сгенерированные баг-репорты не принимаются, сообщать можно только о том, что воспроизвёл сам;
- текст держать коротким, сгенерированная проза обычно слишком длинная;
- участие ИИ раскрывать;
- уязвимости только проверенные на актуальной версии и через их процедуру.

Поэтому подробные разборы в этой папке предназначены читателю репозитория, а не трекеру. В трекер идут короткие сообщения, и перед отправкой каждое воспроизведение прогоняется руками.

## Про две придержанные находки

VKJ-006 и VKJ-014 обе касаются границы авторизации, поэтому по принятому здесь правилу подробности не публикуются, пока сопровождающие продукта не ответят.

Обе низкой серьёзности: утекает только факт существования идентификатора, а такое поведение встречается в API часто и иногда выбрано сознательно. Приватное уведомление здесь не про опасность, а про порядок.

VKJ-006 зафиксирована в наборе двумя тестами в `tests/api/authorization/test_existence_disclosure.py`, помеченными как ожидаемо падающие: они формулируют позицию, не ломая сборку, и превратятся в неожиданный успех, если продукт изменит поведение. У VKJ-014 здесь нет ни папки, ни теста вовсе, потому что в исходном коде продукта прямо сказано, что утекающее ею должно было остаться скрытым.

## Как это устроено

Известные расхождения записаны в базовую линию (`src/vikunja_qa/contracts/baseline.py`) с причиной и указанием находки, к которой они относятся. Набор работает в строгом режиме: расхождение, которого нет в базовой линии, роняет тест, который его вызвал. Базовая линия существует только для того, чтобы уже описанное не заглушало новое, и может только сокращаться. В конце прогона печатаются записи, в которые ничего не попало: так нашлась одна, описывавшая дефект, которого у продукта больше нет.

Ожидаемо падающие тесты используются для позиций, которые набор высказывает, но не считает доказанными дефектами. Утверждать текущее поведение там было бы неправильно: это заморозило бы спорное поведение в наборе как желаемое.
