# VKJ-015. Двое добавляют задачу в один проект одновременно, один получает 500

[English](README.md) | Русский

**Серьёзность:** высокая
**Версия:** Vikunja v2.6.0
**Компонент:** создание задачи, внутрипроектный номер задачи (`pkg/models/tasks.go`)
**Окружение:** официальный образ `vikunja/vikunja:2.6.0`, PostgreSQL, стенд из `docker/docker-compose.yml`

## Суть

Задачи, создаваемые в одном проекте в один момент, сталкиваются на внутрипроектном номере. Один вызывающий выигрывает. Все остальные получают **500 Internal Server Error**, и их задача не создаётся.

Шесть вызывающих, один проект, отпущены одновременно:

```
все в одном проекте     {201: 1, 500: 5}
каждому свой проект     {201: 6}
```

Контрольный замер важен: те же шесть вызывающих, пишущих в шесть разных проектов, проходят полностью. Конкуренция именно внутрипроектная, и шести вызывающих для неё не нужно. **Хватает двух**, а двое это обычный случай.

Тело ответа проигравшему не говорит ничего полезного:

```
HTTP/1.1 500 Internal Server Error
{"message":"Internal Server Error"}
```

Причину называет журнал сервера:

```
pq: duplicate key value violates unique constraint "UQE_tasks_tasks_project_index" (23505)
```

## Влияние

Это не артефакт нагрузочного теста. Общий проект это обычное использование продукта, а двое, нажавших «добавить задачу» в одну и ту же секунду, это обычное поведение. Один из них теряет свою задачу и получает сообщение, что сломался сервер.

Ничего не портится: у созданных задач номера остаются различными, и ограничение в базе как раз и не даёт случиться худшему. Вся цена ложится на того, кому отказали, и на того, кто потом будет объяснять эту пятисотку.

Кроме того, продуктом становится небезопасно управлять параллельно из чего угодно ещё: импортер, синхронизирующий клиент или вкладка браузера, создающая несколько задач разом, часть из них потеряет. Повторить запрос можно, но в ответе ничто не говорит, что это имеет смысл: 500 это статус, который клиенты повторяют в последнюю очередь.

## Причина по исходному коду

`createTasks` назначает номер через `setNewTaskIndexes`, которая вызывает `calculateNextTaskIndex`, читает наибольший номер в проекте и прибавляет единицу:

```go
func setNewTaskIndexes(s *xorm.Session, projectID int64, tasks []*Task) (err error) {
	nextIndex, err := calculateNextTaskIndex(s, projectID)
	...
	t.Index = nextIndex
```

Чтение, потом вставка, и ничто эту пару не сериализует. Две транзакции читают один и тот же наибольший номер, вычисляют один и тот же следующий, и вторая вставка упирается в уникальное ограничение `UQE_tasks_tasks_project_index`. Ошибка возвращается как есть и доходит до клиента пятисоткой.

## Шаги воспроизведения

1. Поднять стенд и зарегистрировать учётную запись.
2. Создать один проект.
3. Отправить несколько запросов `PUT /api/v1/projects/{id}/tasks`, отпущенных в один момент, каждый со своего соединения.
4. Сравнить с тем же числом запросов, разложенных по отдельным проектам.

`reproduce.py` в этой папке делает и то и другое, с барьером, чтобы вызовы действительно наложились:

```bash
py docs/findings/VKJ-015-simultaneous-task-creation-500/reproduce.py
```

## Ожидаемый результат

Задача создаётся у каждого вызывающего, кто бы ни писал в тот же момент. Если продукт не может обслужить всех, он отвечает тем, с чем клиент может что-то сделать, например 409, а не 500.

## Фактический результат

Все, кроме одного, получают 500, и их задач не существует.

## Что чинить

Сериализовать назначение номера: выдавать его в той же транзакции под блокировкой строки проекта, либо взять последовательность, либо повторять вставку при ограничении 23505 вместо того, чтобы возвращать его наружу. Повтор это наименьшее изменение, и оно сделало бы столкновение невидимым, чего клиент вправе ожидать от номера, который сервер выбирает за него.

## Связанный тест

`tests/api/concurrency/test_simultaneous_writes.py::test_tasks_created_at_the_same_moment_are_all_created`, помечен как ожидаемо падающий. Соседние тесты в том же модуле проверяют то, что обязано выполняться в любом случае: у принятых задач номера различны, одновременные изменения сохраняют одну из записей, а ни двойное удаление, ни двойное добавление метки не отвечают серверной ошибкой.
