# VKJ-002. The v1 specification does not allow `null` for collections the product returns as `null` when empty

English | [Русский](README.ru.md)

**Severity:** medium
**Version:** Vikunja v2.6.0
**Component:** the first-version API specification
**Environment:** official image `vikunja/vikunja:2.6.0`, PostgreSQL 18, the stand from `docker/docker-compose.yml`

## Summary

The first version of the API specification declares collection fields to be arrays by type, with no null allowed:

```json
{ "type": "array" }
```

The product returns `null` in them when the collection is empty. That is the expected serialisation behaviour in Go: the zero value of a slice or a map turns into `null`, not into `[]` or `{}`.

At least thirteen fields on the main entities are affected:

| Entity | Fields |
|---|---|
| task | `labels`, `assignees`, `attachments`, `reminders`, `related_tasks`, `reactions` |
| project | `views`, `max_permission` |
| view | `bucket_configuration`, `filter`, `filter.order_by`, `filter.sort_by` |
| user | `settings.extra_settings_links` |
| team | `members` |

The `max_permission` field is a case of its own: the specification declares it as the enumeration `[0, 1, 2]`, while the permission type in the product serialises its "unknown" state as `null`, which the enumeration does not allow.

## Why this is a specification defect

The second version of the API specification, generated by the product from its own code, declares the very same fields correctly:

| Field | v1 | v2 |
|---|---|---|
| `labels` | `"array"` | `["array", "null"]` |
| `assignees` | `"array"` | `["array", "null"]` |
| `attachments` | `"array"` | `["array", "null"]` |
| `reminders` | `"array"` | `["array", "null"]` |

The product behaves the same way in both versions. Only the specification differs, and the correct one of the two is the newer.

## Impact

A client generated from the first-version specification in a strictly typed language fails on parsing any task with no labels, no assignees and no attachments, which is the most ordinary case there is. The user has one way round it: declare every collection field optional by hand, ignoring the generated types.

## Reproduction

```bash
python reproduce.py
```

The script creates a user, a project and a task with no labels, then prints the actual response next to both specifications.

## What to fix

Mark nullability in the first-version annotations the same way it is already marked in the second. An alternative that fixes both versions at once: initialise slices and maps with empty values before serialisation, so that the product returns `[]` and `{}`.
