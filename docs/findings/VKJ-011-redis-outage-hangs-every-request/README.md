# VKJ-011. При недоступном Redis запросы не отказывают, а зависают

**Серьёзность:** высокая
**Версия:** Vikunja v2.6.0
**Компонент:** обращение к хранилищу ключей
**Окружение:** официальный образ `vikunja/vikunja:2.6.0`, `VIKUNJA_REDIS_ENABLED=true` и `VIKUNJA_KEYVALUE_TYPE=redis`, стенд из `docker/docker-compose.yml`

**Важное условие:** находка относится к установке, где хранилищем ключей выбран Redis. Это поддерживаемая продуктом конфигурация и обычный выбор для установок, работающих в нескольких экземплярах. При значении по умолчанию, когда хранилище держится в памяти процесса, поведение другое.

## Суть

Если Redis перестаёт отвечать, авторизованные запросы к API **не возвращают ничего**. Замер на чистом стенде:

| Запрос | Результат |
|---|---|
| `GET /api/v1/projects/{id}` | нет ответа за 40 секунд |
| `GET /api/v1/user` | нет ответа за 40 секунд |

Запрос собственного профиля не читает никаких проектных данных, и он тоже не отвечает. То есть затронуто не отдельное место, а общий путь обработки.

## Почему это важнее обычной деградации

Отказ зависимости сам по себе нормален, и от продукта ожидается одно из двух: работать без неё или внятно отказать. Здесь не происходит ни того, ни другого.

Зависание хуже отказа. Соединение удерживается, обработчик занят, и при обычной нагрузке пул исчерпывается за секунды. Обратный прокси перед приложением начинает копить запросы, проверка живости не получает ответа, оркестратор перезапускает контейнер, новый экземпляр упирается в тот же недоступный Redis. Единичный отказ вспомогательного хранилища превращается в полную остановку сервиса.

Для сравнения, отказ объектного хранилища продукт переживает правильно: создание задачи при выключенном MinIO отработало за одну десятую секунды. Значит изоляция зависимостей в продукте есть, и на этом пути её не хватает.

## Шаги воспроизведения

1. Поднять стенд, где хранилищем ключей выбран Redis.
2. Зарегистрировать пользователя и получить токен.
3. Остановить контейнер: `docker compose stop redis`.
4. Выполнить любой авторизованный запрос с ограничением времени в сорок секунд.
5. Вернуть контейнер: `docker compose start redis`.

## Ожидаемый результат

Запрос завершается: либо успешно, если данные из хранилища ключей не обязательны, либо ошибкой за разумное время.

## Фактический результат

Ответ не приходит за сорок секунд.

## Что чинить

Ограничить время обращения к хранилищу ключей и при исчерпании этого времени продолжать без него либо отказывать с внятным кодом. Кэш по своей природе необязателен, и его недоступность не должна блокировать обработку.

## Связанный тест

`tests/resilience/test_dependency_failures.py::TestKeyValueStore::test_the_product_survives_losing_redis`, помечен как ожидаемо падающий.
