# VKJ-011. При недоступном Redis запросы ждут без предела, который ставил бы продукт

[English](README.md) | Русский

**Серьёзность:** высокая
**Версия:** Vikunja v2.6.0
**Компонент:** обращение к хранилищу ключей
**Окружение:** официальный образ `vikunja/vikunja:2.6.0`, `VIKUNJA_REDIS_ENABLED=true` и `VIKUNJA_KEYVALUE_TYPE=redis`, стенд из `docker/docker-compose.yml`

**Важное условие:** находка относится к установке, где хранилищем ключей выбран Redis. Это поддерживаемая продуктом конфигурация и обычный выбор для установок, работающих в нескольких экземплярах. При значении по умолчанию, когда хранилище держится в памяти процесса, поведение другое.

## Суть

Если Redis перестаёт отвечать, первые авторизованные запросы к API **блокируются, пока не сдастся что-то за пределами продукта**. Собственного предела на ожидание продукт не ставит. Замер на чистом стенде:

| Запрос | При живом Redis | Первые вызовы при остановленном | Последующие |
|---|---|---|---|
| `GET /api/v1/user` | 0,01 с | нет ответа за 45 с | 0,08 с |
| `GET /api/v1/projects/{id}` | 0,04 с | нет ответа за 45 с | 0,26 с |

В этой таблице важнее заголовочной цифры две вещи.

Запрос собственного профиля не читает никаких проектных данных — и тоже блокируется. Значит затронуто не отдельное место, а общий путь обработки.

И продукт в итоге отбрасывает зависимость: после первых попыток он перестаёт ждать хранилище и обслуживает остальное за четверть секунды. Дефект не в том, что он не может жить без кэша — может, — а в том, что выяснение этого занимает неограниченное время, и всё это время страдает каждый запрос.

## От чего это зависит, а от чего нет

**Эта находка была заявлена сильнее, чем есть на самом деле**, и поправку стоит назвать вслух, а не переписать втихую. Изначально отчёт утверждал, что запросы «не возвращают ничего», без оговорок. Прогон воспроизведения на линуксовом раннере CI вместо Docker Desktop под Windows дал ответ за 2 секунды, а не зависание, — и отчёт в прежнем виде этого не пережил.

Меняется *длительность* ожидания, и это дело хоста, а не продукта. Остановленный контейнер оставляет свой адрес недостижимым, а сколько попытка соединения с недостижимым адресом длится до отказа — свойство сетевого стека между ними:

| Где | При живом Redis | Первый вызов при остановленном |
|---|---|---|
| Docker Desktop под Windows, через его проброс портов | 0,03 с | нет ответа за 25–45 с |
| линуксовый раннер CI, напрямую через мост | 0,00 с | 2,0 с |

Не меняется вклад самого продукта: и там, и там вызов на общем пути ждёт, пока решит сеть, потому что продукт её об этом просит. Две секунды на пути входа — уже достаточно, чтобы исчерпать пул соединений под нагрузкой, а сорок — чтобы провалить проверку живости и дождаться перезапуска контейнера оркестратором в тот же недоступный Redis.

Так что находка остаётся в силе, и её утверждение теперь то, которое воспроизводится везде: **продукт не ставит собственного таймаута на хранилище ключей, на пути, по которому идёт каждый авторизованный запрос.** Воспроизведение проверяет именно это — сравнением с тем же вызовом при живом хранилище, а не числом, которого оно не может обещать.

## Почему это важнее обычной деградации

Отказ зависимости сам по себе нормален, и от продукта ожидается одно из двух: работать без неё или внятно отказать — за время, которое он выбирает сам. До первого продукт в итоге доходит: без хранилища он работает. Но не за время, которое выбрал сам.

Ожидание хуже отказа — ровно столько, сколько длится. Соединение удерживается, обработчик занят, и при обычной нагрузке пул исчерпывается в этом окне. Обратный прокси начинает копить запросы, проверка живости ждёт вместе со всеми, а там, где ожидание достаточно длинное, оркестратор перезапускает контейнер — в тот же недоступный Redis.

Для сравнения, отказ объектного хранилища продукт переживает правильно: создание задачи при выключенном MinIO отработало за одну десятую секунды. Значит изоляция зависимостей в продукте есть, и на этом пути её не хватает.

## Шаги воспроизведения

1. Поднять стенд, где хранилищем ключей выбран Redis.
2. Зарегистрировать пользователя и получить токен.
3. Остановить контейнер: `docker compose stop redis`.
4. Выполнить любой авторизованный запрос, засекая время, с щедрым ограничением.
5. Повторить его ещё дважды, засекая каждый.
6. Вернуть контейнер: `docker compose start redis`.

## Ожидаемый результат

Каждый запрос завершается за время, которое решает продукт: успешно, если хранилище ключей для него не нужно, либо внятной ошибкой.

## Фактический результат

Первые запросы длятся столько, сколько хост отказывается от соединения: две секунды на линуксовом мосту, десятки секунд через проброс портов Docker Desktop. Следующие обслуживаются нормально — продукт к тому моменту перестаёт ждать хранилище.

## Что чинить

Ограничить время обращения к хранилищу ключей и при исчерпании этого времени продолжать без него либо отказывать с внятным кодом. Кэш по своей природе необязателен, и его недоступность не должна блокировать обработку.
