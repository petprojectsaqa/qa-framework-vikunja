# VKJ-013. После перезапуска почтового сервера почта не идёт совсем, пока не наступит пауза

[English](README.md) | Русский

**Серьёзность:** высокая
**Версия:** Vikunja v2.6.0
**Компонент:** демон исходящей почты (`pkg/mail/mail.go`)
**Окружение:** официальный образ `vikunja/vikunja:2.6.0`, почта включена, стенд из `docker/docker-compose.yml`

## Суть

Если SMTP-сервер перезапустился или по любой причине разорвал соединение, демон почты Vikunja не переподключается, пока почта продолжает идти. Он держит открытое ранее соединение, пробует каждое сообщение из очереди на этом мёртвом соединении, и каждое падает. Переподключается он только после того, как очередь **простаивает 30 секунд `mailer.queuetimeout`**.

То есть восстановление зависит от трафика, а не от того, что сервер вернулся. На тихом инстансе одно следующее сообщение переподключит демон и пройдёт. На нагруженном, где сообщения идут чаще чем раз в 30 секунд, таймер простоя не срабатывает никогда, и **всё теряется, пока идёт трафик**: подтверждения, сбросы паролей, напоминания, и всё это молча.

Замер на стенде, одна регистрация каждые 5 секунд после возврата почтового сервера:

```
доставлено, пока шёл трафик (25с):   нет
доставлено после паузы в 35с:        да
```

Продукт пишет каждую неудачу в журнал, так что администратору с открытым логом это видно, но пользователю ничего не показывается и потерянное сообщение не переотправляется:

```
level=ERROR msg="Error when sending mail: checking SMTP connection: not connected to SMTP server"
```

## Влияние

Чем нагруженнее инстанс, тем хуже и дольше отказ: ровно наоборот тому, что ожидает администратор. Мелкий сбой почтового сервера, который должен стоить нескольких секунд задержки, вместо этого стоит всех писем до тех пор, пока трафик случайно не затихнет на полминуты, а на активном инстансе этого можно ждать долго. Ничего не переотправляется, поэтому письма из этого окна потеряны.

Сброс пароля и подтверждение адреса это как раз те письма, которых пользователь активно ждёт, поэтому для него это выглядит как учётная запись, в которую он больше не может войти.

## Причина по исходному коду

`StartMailDaemon` в `pkg/mail/mail.go` крутит одну горутину вокруг `select`. Сообщение подключается, если `open` ложно, и отправляет; таймаут в 30 секунд без сообщений закрывает соединение и ставит `open = false`.

```go
case m, ok := <-queue:
    ...
    if !open {
        err = c.DialWithContext(context.Background())
        ...
        open = true
    }
    err = c.Send(m)
    if err != nil {
        log.Errorf("Error when sending mail: %s", err)
        break            // open остаётся true
    }
case <-time.After(config.MailerQueueTimeout.GetDuration() * time.Second):
    if open {
        open = false     // единственный путь, где он сбрасывается
        c.Close()
    }
```

Неудачная отправка пишет в лог и делает `break`, но оставляет `open` истинным, поэтому следующее сообщение пропускает переподключение и отправляется на том же мёртвом соединении. Единственное, что вообще сбрасывает `open`, это таймаут простоя, а постоянный трафик заново взводит его таймер, не давая сработать.

## Шаги воспроизведения

1. Поднять стенд и убедиться, что почта доставляется.
2. `docker compose stop mailpit`, затем `docker compose start mailpit`.
3. Провоцировать письмо (регистрация или сброс пароля) каждые несколько секунд в течение полуминуты. Ни одно не приходит.
4. Перестать провоцировать больше чем на 30 секунд, затем спровоцировать ещё одно. Оно приходит.

`reproduce.py` в этой папке делает всё это, сам поднимая и опуская почтовый сервер стенда, и печатает два исхода:

```bash
py docs/findings/VKJ-013-mail-daemon-stale-connection/reproduce.py
```

## Ожидаемый результат

Как только почтовый сервер снова доступен, письма из очереди и последующие доставляются в срок, который не зависит от того, затих ли трафик.

## Фактический результат

Пока почта идёт чаще чем раз в 30 секунд, не доставляется ничего. Переподключиться демону даёт только пауза в 30 секунд.

## Что чинить

Сбрасывать `open` (и закрывать соединение) при неудачной отправке, чтобы следующее сообщение переподключалось. Переподключение с небольшой задержкой на пути отправки превратило бы сбой почтового сервера в короткую задержку, а не в открытый по времени отказ. Неудачные сообщения стоит возвращать в очередь, а не терять.
