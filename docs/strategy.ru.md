# Стратегия и архитектура

[English](strategy.md) | Русский

Документ отвечает на вопрос «как это устроено». Вопрос «что проверяется» остаётся за [матрицей покрытия](coverage-matrix.ru.md). Читать их нужно вместе.

Каждое решение ниже принято под конкретный объект тестирования, и большинство из них опирается на факты, взятые из его исходного кода. Там, где решение спорно, названа отвергнутая альтернатива и причина отказа. Это сделано намеренно: документ должен выдерживать вопрос «а почему не иначе».

---

## 1. Изоляция, решение, из которого следует всё остальное

Объект тестирования это одно работающее приложение над одной базой. Тесты должны идти параллельно и не мешать друг другу. Способов сделать это четыре, и выбор между ними определяет весь остальной дизайн.

**Отвергнуто: очистка базы между тестами.** У продукта есть служебный API, опустошающий все таблицы. Соблазнительно и смертельно для параллельности: пока один тест чистит базу, все остальные теряют свои данные.

**Отвергнуто: откат транзакции.** Классический приём модульных тестов здесь неприменим, потому что приложение это отдельный процесс со своим пулом соединений. Транзакция теста ему не видна.

**Отвергнуто: разделение по именам.** Слабая изоляция, которая держится на дисциплине фильтрации и рассыпается при первой же ошибке в запросе.

**Принято: изоляция по владельцу.** В Vikunja всё принадлежит пользователю: проекты создаёт пользователь, задачи живут внутри проектов, права выдаёт владелец. Два теста, работающие под разными пользователями, физически не видят данных друг друга. Изоляция становится свойством конструкции, а не уборки.

Каждый тест по умолчанию получает свежие учётные записи, созданные через обычную ручку регистрации, вместе с подтверждением по почте, потому что на стенде почта включена.

Следствия, если принимать их честно:

- Регистрация стоит одного обращения к продукту на каждое действующее лицо в тесте. Это плата за изоляцию, и она принята осознанно. Если замер когда-нибудь покажет, что здесь узкое место, тогда и придёт время это оптимизировать.
- **Порождаемые семейства пользуются одной учётной записью на весь прогон.** Они только читают, и их сотни; заводить там отдельные записи не даст ничего.
- Уборка между тестами не нужна вообще. Ничего не удаляется, поэтому после красного прогона данные, которые к нему привели, остаются на месте, и в них можно заглянуть.

**Что нельзя изолировать по владельцу.** Список всех пользователей, счётчики метрик, глобальная конфигурация, действия администратора инстанса и ограничение частоты запросов общие для всех. На практике сегодня к этому общему состоянию обращается только одна группа набора, слой устойчивости, и он запускается отдельно.

**Правило для метрик.** Счётчики глобальные, поэтому утверждения о них строятся на разнице, измеренной вокруг действия. Абсолютные значения не утверждаются.

## 2. Служебный API продукта

Продукт предоставляет две служебные ручки, включаемые секретом в его конфигурации: опустошить все таблицы и наполнить одну таблицу заданным содержимым.

Правило их использования строгое, потому что соблазн велик.

**Разрешено в двух случаях.** Первый: однократный сброс перед началом прогона. Второй: подготовка состояний, недостижимых через публичный API, например уже истёкшего токена, пользователя с флагом администратора инстанса или записи с датой в прошлом.

**Запрещено во всех остальных.** Обычные данные готовятся только через публичный API. Причина не стилистическая: тест, собирающий состояние за спиной у продукта, проверяет собственное представление о его схеме, а не сам продукт. Он ломается на первой же миграции и не находит настоящих дефектов.

Каждое обращение к служебному API помечено в коде и попадает в отчёт отдельным шагом, чтобы читателю было видно, где срезан угол и почему.

## 3. Слои

Фреймворк это стопка слоёв с односторонней зависимостью. Обращение вверх считается дефектом архитектуры.

```
tests                 утверждения, и только они
  ↓
vikunja_qa.testing    сторона pytest: фикстуры, соглашения, плагин
  ↓
scenes                декларативная сборка состояния
  ↓
actors                личность, её удостоверение и привязанные к нему клиенты
  ↓
clients               типизированные клиенты по областям API и дверь CalDAV
  ↓
transport             HTTP, отчётность, проверка контракта
  ↓
config, domain        настройки и словарь самого продукта
```

Объекты страниц стоят сбоку и опираются на те же слои, потому что готовят данные вызовами API, а не кликами.

Правила, и каждое из них проверяется:

- **Ни один тест не говорит по HTTP напрямую.** Тест добирается до продукта через клиентов, поэтому каждый вызов помечен удостоверением, записан в отчёт и проверен на соответствие контракту.
- **Ниже слоя тестов нет ни одного утверждения.** Клиент возвращает ответ, а решение о его правильности принадлежит тесту. Утверждение уровнем ниже превращает дефект продукта в ошибку фреймворка, не в том файле и не с тем сообщением.
- **Объект страницы не содержит утверждений.** Он умеет действовать на странице и читать её, а судит тест.
- **Транспортный слой не знает предметной области.** Он никогда не слышал ни о задачах, ни о проектах.
- **О pytest знает только `vikunja_qa.testing`.** Всё остальное остаётся пригодным к запуску из обычного скрипта, на чём и держатся скрипты воспроизведения и проверка стенда.

Это не проза. `tests/unit/test_layers.py` разбирает исходники и роняет сборку, когда стрелка смотрит не туда. Архитектура, описанная только словами, разъезжается на третьем месяце.

## 4. Действующее лицо как объект

Центральная абстракция. Действующее лицо связывает вместе личность, удостоверение, которое её подтверждает, и клиентов, привязанных к этому удостоверению.

Продукт поддерживает четыре независимых способа подтвердить личность, и матрице доступа нужны все четыре:

| Способ | Как получается | Где применяется |
|---|---|---|
| Токен сессии | обмен логина и пароля | основная масса набора |
| API-токен | выдаётся в настройках, `tk_` плюс сорок символов | матрица областей действия |
| Токен публичной ссылки | обмен хеша, при необходимости с паролем | проверки доступа по ссылке |
| HTTP Basic | логин и секрет в заголовке | календарный протокол |

Токен сессии по умолчанию живёт трое суток, поэтому токен, выданный в начале прогона, остаётся действительным до его конца.

Тест не собирает действующее лицо руками. Он называет роль, а фабрика строит весь граф: владельца, проект, второго зарегистрированного пользователя, выданное право и команду, если роль её требует.

`actor.using(credential)` это та же личность, пришедшая другим способом, и именно это превращает матрицу доступа в таблицу, а не в груду почти одинаковых тестов.

## 5. Сборка состояния

Набор такого размера остаётся читаемым только тогда, когда подготовка состояния объявляется, а не программируется.

Вместо десятков мелких фикстур есть один строитель сцены. Тест описывает нужный ему мир одной цепочкой, строитель выполняет вызовы в правильном порядке и возвращает один объект, через который доступны все действующие лица и все созданные сущности.

```python
world = scene.project().member("reader", Permission.READ).task().done()
```

Что гарантирует строитель:

- **Одинаковое описание даёт одинаковую структуру**, различия только в идентификаторах.
- **Не создаётся ничего, чего тест не запросил.**
- **Каждый шаг сборки попадает в отчёт отдельной строкой**, поэтому при поломке подготовки сразу видно, что сломалась именно подготовка и где.
- **Имена несут происхождение.** Каждое сгенерированное имя содержит идентификатор теста и номер исполнителя, поэтому строка, оставшаяся в базе после красного прогона, указывает на создавший её тест.

Неудача при сборке мира поднимает `SetupError`, а не падение утверждения, потому что она означает, что до самой проверки, ради которой писался тест, дело так и не дошло.

## 6. Проверка контракта как побочный эффект

Обычный подход это отдельный набор контрактных тестов. Здесь сделано иначе.

**Каждый ответ на каждый вызов в каждом тесте проверяется против схемы своей операции, на транспортном слое.** Контрактные тесты не пишутся: контрактное покрытие возникает побочным эффектом любого взаимодействия с продуктом.

Описания забираются с работающего инстанса, а не из репозитория продукта, поэтому проверяется именно та сборка, которая реально поднята. v1 отдаёт Swagger 2.0, v2 отдаёт OpenAPI 3.1, генерируемый на лету.

Уже описанные расхождения лежат в базовом списке вместе с находкой, к которой относятся. Набор работает строго: расхождение, которого нет в базовом списке, роняет обнаруживший его тест. Базовый список существует для того, чтобы известное не заглушало новое, и **он может только сокращаться**. В конце прогона печатаются записи базового списка, в которые ничего не попало, и именно так выяснилось, что одна запись описывала дефект, которого у продукта больше нет.

Побочная выгода, которую стоит иметь: **покрытие операций считается по фактически сделанным вызовам**, а не по намерениям.

## 7. Ожидание асинхронного

Ни одной фиксированной паузы вместо ожидания в наборе нет. Это не пожелание, а принуждение: `tests/unit/test_layers.py` роняет сборку на `time.sleep` внутри набора.

Вместо пауз есть `wait_until`, который опрашивает условие с предельным сроком и нарастающим интервалом. Каждое применение указывает свой бюджет времени и, в аргументе `because`, чего именно оно ждёт, поэтому таймаут объясняет себя сам, а не сообщает, что время вышло.

Причина строгости простая. Пауза на две секунды и медленнее, и ненадёжнее ожидания: на быстрой машине она тратит разницу впустую, на нагруженной всё равно мигает.

**Единственное исключение, названное, а не спрятанное.** Модулю устойчивости почты настоящая пауза разрешена, потому что ему нужно дать истечь таймеру внутри продукта, а таймер опросом не наблюдается. Это единственный файл в списке разрешений, и сам список лежит в тесте.

## 8. Утверждения

Три требования к каждому утверждению в наборе.

**Полный контекст в сообщении.** Каждый ответ умеет описать себя: метод, URL, использованное удостоверение, отправленное тело, статус, доменный код ошибки и тело ответа. Упавшее утверждение печатает всё это, поэтому первого взгляда на падение обычно хватает.

**Падение называет суть, а не форму.** Сообщения говорят, что сделал продукт и почему это неправильно, словами самого продукта.

**Отчёт несёт доказательства.** Тела запроса и ответа прикладываются к каждому шагу, а упавший браузерный тест прикладывает ещё и экран, и исходный код страницы.

Отдельно: код ответа и доменный код ошибки проверяются вместе. Утверждение только по статусу слабое, потому что 400 отдаётся по десяткам причин.

## 9. Параллельный запуск

По умолчанию всё идёт параллельно, потому что изоляция по владельцу это позволяет. Слой api работает на восьми исполнителях, браузерный на четырёх.

Исключение это слой устойчивости, который гасит контейнеры, общие для всего стенда. Последствия нельзя удержать внутри вызвавшего их теста, поэтому в основной прогон он не входит никогда, а плагин отказывается принимать `--resilience` вместе с `-n`, вместо того чтобы полагаться на чью-то память.

Контрактное покрытие собирается на каждом исполнителе и сводится на управляющем процессе, поэтому итог в конце прогона относится ко всему прогону, а не к доле одного исполнителя.

## 10. Политика нестабильности

Позиция выбрана намеренно и вынесена в README, потому что сама по себе она о многом говорит.

- **У слоя api повторов нет вообще.** Ноль. Мигающий тест API это либо дефектный тест, либо настоящая гонка в продукте. И то и другое требует разбора, а не повтора.
- **У браузерного слоя ровно один повтор**, и на повторе пишется трассировка. Повтор здесь инструмент диагностики, а не способ получить зелёный прогон.
- **Тест, которому повтор понадобился, чинится или удаляется.** Третьего не дано.

## 11. Отчётность

Шаги отчёта порождаются на уровне клиентов, а не пишутся руками в тестах. Расставленные вручную шаги замусоривают тест и всегда отстают от кода.

Метки вычисляются, а не объявляются. Расположение теста даёт эпик, функциональность и историю; объявленные им проверки матрицы дают серьёзность и ссылку на строку матрицы; маркер `finding` или `advisory` добавляет ссылку на описание находки или на бюллетень. Это даёт прослеживаемость в обе стороны, от строки матрицы к тестам и обратно, и разъехаться она не может, потому что одна сторона вычисляется из другой.

Вложения идут через одно место, `vikunja_qa.reporting`, которое молчит, когда ни один тест не выполняется. Это не украшение: попытка приложить что-то к Allure вне теста бросает исключение, и какое-то время из-за этого на этапе сбора молча пропадало целое порождаемое семейство.

## 12. Собственное качество фреймворка

Инструмент тестирования без собственных тестов это анекдот, и проверяющий замечает это первым.

Модульный слой покрывает те части, где ошибка была бы незаметна: загрузку и сопоставление спецификаций, базовый список, помощник ожидания, чтение и запись iCalendar, генераторы семейств областей действия и сплошного обхода, каталог прослеживаемости, соглашения, журнал, который переживает границу процессов, и транспорт, проверяемый на заготовленном адаптере, чтобы настоящий клиент выполнял свой настоящий код без сети.

Три из этих тестов проверяют репозиторий, а не код: разделение на слои, документацию против набора, который она описывает, и соглашения, применяемые запуском плагина на маленьких одноразовых деревьях тестов через собственный `pytester` из pytest.

**Модульный слой выполняется с запретом исходящих соединений.** Тест, который незаметно начал зависеть от живого сервиса, падает сразу и говорит об этом, а не проходит на машине разработчика и падает в задаче, где стенда нет.

## 13. Стенд

Восемь контейнеров: приложение, PostgreSQL, Redis, MinIO, перехватчик почты, приёмник вебхуков, Prometheus и Grafana.

Стенд отличается от боевой установки намеренно:

- Ограничение частоты запросов выключено, и вдобавок подняты три предавторизационных порога, потому что этот порог не подчиняется общему выключателю и параллельный прогон упирается прямо в него.
- Служебный API включён своим секретом.
- Файлы уходят в объектное хранилище, а не на диск, чтобы под проверкой оказался более сложный путь.
- Почта уходит в перехватчик, и регистрация действительно проходит через ссылку подтверждения.
- CalDAV включён, и это значение по умолчанию у самого продукта.

Прогон не начинается, пока `scripts/check_stand.py` не скажет, что стенд готов. Скрипт проходит один настоящий пользовательский путь от начала до конца, поэтому зелёный результат что-то значит, и пользуется только стандартной библиотекой, потому что запускается раньше, чем зависимости проекта обязательно существуют.

## 14. Сборка

Семь задач, разделённых по скорости и по тому, что им нужно.

| Задача | Что делает | Нужен стенд |
|---|---|---|
| стиль, типы, слои | ruff, ruff format, mypy | нет |
| собственные тесты фреймворка | модульный слой | нет |
| дымовой прогон | критический путь по обоим слоям | да |
| набор api | основной прогон, восемь исполнителей, ворота покрытия P0 | да |
| браузерный набор | Playwright, один повтор, трассировки при падении | да |
| отказы зависимостей | слой устойчивости, по расписанию и по требованию | да |
| отчёт | собирает и публикует отчёт Allure | нет |

Быстрые задачи идут первыми и отсекают сломанное изменение за секунды. Дымовой прогон стоит воротами перед двумя полными наборами. Слой устойчивости в основную цепочку не входит вовсе.

## 15. Технологии и почему они

| Что | Чем | Почему |
|---|---|---|
| язык | Python | язык автора и его целевой аудитории |
| зависимости | uv | скорость и воспроизводимая фиксация версий |
| запуск | pytest | стандарт, с системой плагинов, на которую опирается этот дизайн |
| параллельность | pytest-xdist | распределение и управляющий процесс, способный свести то, что узнали исполнители |
| HTTP | requests | покрывает всё, что здесь нужно |
| настройки | pydantic-settings | типизированная конфигурация из окружения |
| схемы | jsonschema | Draft 4 для Swagger 2.0 и 2020-12 для OpenAPI 3.1 |
| база данных | psycopg | прямые запросы для проверок целостности, только на чтение |
| браузер | Playwright | собственные фабрики, трассировки и видео, переиспользованные, а не написанные заново |
| отчёт | Allure | читаемый результат и метки, которые можно вычислять |
| стиль и типы | ruff, mypy | быстро, строго и одинаково локально и в CI |
| слои | собственный модульный тест набора | архитектура закреплена, а не описана |

## 16. Порядок, в котором это строилось

Порядок выбран так, чтобы каждый шаг заканчивался чем-то работающим целиком, а не половиной трёх слоёв.

1. **Стенд и настройки.** Compose, ворота готовности, профили окружения.
2. **Транспорт и подтверждение личности.** Клиент, отчётность, четыре удостоверения, действующее лицо.
3. **Проверка контракта внутри транспорта.** Загружены оба описания, проверяется каждый ответ.
4. **Клиенты по областям и строитель сцены.** Состояние становится одной строкой.
5. **Порождаемые семейства.** Авторизация, области действия токенов, сплошной обход задокументированных операций.
6. **Матрица доступа по хребту.**
7. **Целостность через базу данных и асинхронные эффекты.**
8. **Согласованность между двумя версиями API.**
9. **Регрессии на опубликованные уязвимости.**
10. **Браузерный слой поверх готовых фабрик.**
11. **Слой устойчивости, отдельно от всего.**
12. **Календарный срез, плагин соглашений, ворота покрытия и оформление находок.**

Первые четыре шага это скелет. После них набор растёт линейно, и новых архитектурных решений принимать уже не приходится.
